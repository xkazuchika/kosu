## Context

動機と段階的な改善方針は proposal.md を参照。

- `monthly-plans.admin.tsx` は月次予定の明細と稼働可能時間を別々に表示する。既存の入力を残して一覧を上部に追加できる。
- 月次予定のキーは担当者・案件・月・役割。案件単位の一覧では役割を合算する必要がある。
- `reports.planned-vs-actual.tsx` はすでに担当者・案件ごとに予定と実績を集計するが、予定が空でも稼働可能時間を未予定として表示し、確認状態を持たない。
- `monthly_plans`、`member_monthly_capacities` に確認情報はない。CSV も書き込み経路に含まれるため、画面だけで確認を解除すると漏れが生じる。
- 月次保護は原価締めと共通。今回の確認は入力内容の確認であり、実績提出・原価承認とは別。

## Goals / Non-Goals

**Goals:** 既存の予定値を唯一の月次配分データとして使い、一覧と予実比較で共通の余力計算を行う。確認とその解除を同時更新に対して整合させる。

**Non-Goals:** 新しい予定入力方式、日次予定との同期、実績提出のゲート追加、締め状態の変更、原価スナップショットの再計算。

## Decisions

### 1. 既存画面を拡張し、共通の集計サービスを利用する

`app/services/monthly-allocation-overview.ts` に時間だけの集計を置く。月次予定、稼働可能時間、確認状態を月単位で取得し、担当者×案件を Map で合算する。メンバー・案件の表示項目を明示的に選び、単価や認証情報を新しい DTO に含めない。管理者画面と予実比較から利用し、メンバーへの返却は本人分に限定する。

別のリソース管理画面を作る案より、既存の予定編集と同じ月・同じ場所で判断できる利点を優先する。一覧の合計にはアーカイブ案件や解除済みアサインの保存予定も含め、状態を表示する。案件列は選択月に予定がある案件とし、無効メンバーは履歴として表示する。

### 2. 管理者が担当者・月の予定を確認する

提案上の初期運用は、予定の入力者である管理者が各行の「予定を確認」を押す方式。従業員への新しい提出義務は追加しない。確認なしでも予定の保存、実績入力、提出、原価締めを利用できる。

`member_monthly_plan_reviews` を追加する。担当者・月を UNIQUE とし、非負整数の revision、nullable の confirmedByMemberId / confirmedAt を持つ。月形式と revision の DB 制約、外部キーを設ける。行なしは revision 0・未確認として扱う。

予定とキャパシティの INSERT / UPDATE / DELETE に SQLite trigger を設け、対象の review 行を upsert、revision を増加し確認者・時刻をクリアする。UPDATE は予定の担当者・案件・月・役割・時間、キャパシティの担当者・月・時間の列を対象とし、原価スナップショットのみの修正は除く。旧・新の対象が違う場合は両方に適用する。

各 route / import で解除処理を書く案より DB trigger で全経路と原子性を揃える。直接 DB 更新も含めて漏れを防ぎ、失敗・rollback 時は revision も戻る。

確認 form は表示時 revision を送り、書き込み transaction 内で管理者権限、有効メンバー、実在月、未締め、revision 一致を検証して確認者・時刻を保存する。古い form は再確認を案内する。GET は revision と予定値を一貫した読み取り transaction で取得する。

### 3. 余力の計算と表示を分ける

計算上の残りは capacity − 月次予定合計。capacity が null なら残りも null、0 なら既知のゼロ。超過は確認前でも警告する。正の残りは確認済みの有効メンバーだけ「予定上の余力」と表示し、未確認は「未確認（仮の残り …h）」とする。無効メンバーを追加配分候補にしない。

確認済みでも週内の空きやスキル適合は保証しないことをガイドに記載する。実績時間は予定残高から再度引かない。自動的に予定入力済み＝確認済みとする案は、一部しか入力していないケースを区別できないため採用しない。

### 4. 月次の配分判断を画面の先頭に置く

対象月、担当者×案件表、予定編集、任意の稼働可能時間という順にする。予定合計、稼働可能時間、確認状態、余力・超過は行単位で比較できる配置にする。小画面は横スクロールと担当者の識別を確保し、色だけで状態を伝えない。予実比較へのリンクは対象月を引き継ぐ。

日次予定の自動作成や入力必須化はせず、月次＝配分、日次＝任意の段取りという説明に揃える。

## Risks / Trade-offs

- 確認操作が増える → 担当者ごとに一操作とし、未確認でも通常の業務は止めない。
- trigger が通常の repository から見えにくい → migration とサービスに意図を記載し、CSV、直接更新、rollback を DB テストで保証する。
- 古い保護月は未確認になる → 移行で確認を捏造せず、履歴の予定として表示する。確認のための再オープンは要求しない。
- 月単位では週ごとの偏りが分からない → 月単位の目安と明記し、週次配分は実運用で必要性を確認して別途検討する。

## Migration Plan

1. Drizzle の追加 migration で review テーブル・制約・trigger を作成する。既存予定・キャパシティ・締め・財務 snapshot は更新しない。
2. 空 DB と既存データあり DB の両方で migration、既存値保持、trigger、権限・月次保護の確認を行う。
3. 通常 CI とブラウザー確認後、通常のリリース手順に進む。今回の計画作成では公開しない。
4. アプリだけ旧版へ戻す場合、追加テーブルは残せるが旧版に確認表示はない。旧版の予定書き込みでも trigger は確認を解除する。スキーマ自体の復元が必要なら移行前バックアップを利用する。

## Subsequent Improvements

次の変更は工数確定と原価確定の分離。既存の `monthly-cost-close` と保護経路、承認済み snapshot を保ちながら、単価・契約額なしで工数確定できる仕様を別途作る。既存の保護を単に解除したり、単価欠損をゼロ円として扱ったりしない。

その後に担当者×案件の実績内訳と推移、社内作業の分類、案件の残作業見込みを検討する。簡易原価は保存時間×概算単価を中心とし、費用範囲を表示する。後続の仕様・実装を本変更の完了条件には含めない。
