## Context

動機は `proposal.md - Why` を参照。ここでは実装判断に必要な現状と制約のみを述べる。

- DB は better-sqlite3 + Drizzle。接続はリクエストごとに `createDatabaseConnection()` で生成し `finally` で close する運用が全ルートで徹底されている。`app/db/client.ts` には pragma 設定が一切無い。
- SQLite は既定で `foreign_keys = OFF`。そのため `app/db/schema.ts` の全 `references()` と `onDelete: "cascade" | "restrict"` が実行時に強制されず、`app/services/import.ts` の参照不整合を捕捉する `catch` も発火しない。
- `journal_mode` と `busy_timeout` も未設定。SQLite は単一ライターであるため、同時書き込みは即 `SQLITE_BUSY` を返し得る。リトライ機構は無い。
- `journal_mode = WAL` は DB ファイルに永続する設定。`foreign_keys` と `busy_timeout` は接続単位の設定。
- 前 change で import commit はトランザクション化済み。しかしテンプレート必須列がヘッダ行に存在しない場合、レコードの該当プロパティが `undefined` になって数値バリデーションのガードを通過し、`Number(undefined) = NaN` が INSERT されてトランザクション全体が失敗する。結果は「0 件インポート」で、利用者からは原因が見えない。
- `app/routes/work-logs.$date.tsx` の編集セレクトは `assignedProjects`（現在アクティブなアサインの案件のみ）で構成される。既存 allocation の `projectId` が含まれない場合、HTML の `<select>` は一致する `<option>` が無いため先頭を選択状態にし、保存時に別案件へ工数が移動する。サーバー側 `validateAllocationTarget` は「有効かつアサイン済みか」しか検証しないため、暗黙の付け替えを通してしまう。
- `app/` 内にログ出力が皆無（`console.*` も外部ロガーもなし）。`app/root.tsx` の ErrorBoundary は汎用メッセージを表示するだけで詳細を記録しない。`/health` 系のエンドポイントも存在しない。
- ログインレート制限は前 change で導入済みだが、`X-Forwarded-For` を無検証で信頼する点は既知の限界として README に文書化されている。

## Goals / Non-Goals

**Goals:**

- スキーマに宣言された外部キー制約が実行時に実際に強制されること
- 同時書き込みが即座に失敗せず、設定した時間だけリトライされること
- 外部キー有効化の前に既存データの孤立を検出し、壊れた状態で運用を開始しないこと
- CSV テンプレートの必須列欠落が、原因の分かるエラーとして利用者に伝わること
- 既存実績配賦の案件が、編集操作によって暗黙に別案件へ付け替わらないこと
- 外部ヘルスチェックと、障害発生時に追跡できる最小限の記録手段があること

**Non-Goals:**

- DB 接続のシングルトン化。プラグマは接続生成時に設定すれば現在の「リクエストごとに開閉」構成でも正しく働くため、本 change では不要。全ルート変更を伴うため別 change で検討する
- Dockerfile のマルチステージ化・非 root 実行（別 change）
- 本格的な構造化ロギング基盤（外部ライブラリ）の導入。標準出力への最小記録にとどめる
- メトリクス収集、分散トレーシング、外部監視サービスとの連携
- リクエストログの全件記録とアクセス解析
- ログインレート制限の `X-Forwarded-For` 信頼モデルの見直し（前 change で既知の限界として文書化済み）
- ダッシュボードの N+1 クエリ解消と一覧画面のページネーション（データ量が増大してから別 change で扱う）

## Decisions

1. **プラグマは `createDatabaseConnection()` 内で設定する**
   - `foreign_keys = ON`、`journal_mode = WAL`、`busy_timeout = 5000` を接続生成時に実行する。
   - 理由: 接続はリクエストごとに生成されるため、接続単位の設定（`foreign_keys` / `busy_timeout`）はここが唯一確実な適用箇所。`journal_mode` は永続設定だが毎回実行しても冪等で安価。
   - 代替案: 接続をシングルトン化して起動時に一度だけ設定 → 全 26 ルートの `createDatabaseConnection()` / `sqlite.close()` を書き換える必要があり範囲が広すぎるため不採用。

2. **外部キーは「検査してから有効化」の順で導入する**
   - 検査は `app/db/integrity.ts` の `findForeignKeyViolations()` に切り出し、CLI の `scripts/check-foreign-keys.ts`（`npm run db:check`）から実行する。違反がある場合は対象テーブルと親テーブル、件数を含むメッセージを標準エラーに出し、終了コード 1 で終了する。
   - 起動時の実行は `db:migrate` を `drizzle-kit migrate && npm run db:check` に繋ぐことで実現する。マイグレーションは drizzle-kit CLI が担っており TS 側の `runMigrationsAndClose` はコンテナ起動経路で使われていないため、npm script を繋ぐ方が実態に合う。`npm run dev` と Docker の `CMD`（いずれも `npm run db:migrate` を先に実行する）は、違反時にそのまま起動を止める。
   - データベースファイルが存在しない場合は検査をスキップして成功とする（初回起動を妨げないため）。
   - 理由: 孤立行を抱えたまま `foreign_keys = ON` で運用すると、参照先の無い行の扱いが予測不能になる。黙って有効化するより、運用者に修復を促す方が安全。
   - 代替案: 有効化時に違反行を自動削除 → 削除はデータ損失を伴う判断であり、システムが自動で行うべきではないため不採用。修復手順は README に記載し人手で行う。

3. **CSV 必須列の欠落はプレビュー時に列レベルで検出する**
   - `app/services/import.ts` に種別ごとの必須ヘッダ一覧を定義し、ヘッダ行に存在しない列がある場合は行の内容に関わらずプレビューを失敗させる。
   - 理由: 現状は列欠落が `undefined` として数値ガードをすり抜け、`NaN` の INSERT がトランザクション全体を巻き添えにする。行レベルのエラーにしてしまうと原因（列が無い）と症状（各行の値が不正）がずれる。
   - 列は存在するが値が空欄の場合は従来どおり数値バリデーションの対象とし、列欠落とは異なるメッセージを返して切り分け可能にする。

4. **既存配賦の案件は「表示に残す」と「暗黙変更を拒否する」の両面で守る**
   - 表示側: `app/routes/work-logs.$date.tsx` の案件セレクトは、編集中の allocation が参照する案件を選択肢に必ず含め、解除済み・アーカイブ済みであることをラベルで示す。
   - サーバー側: 既存 allocation の更新では、送信された `projectId` が元の `projectId` と同一ならアサイン・アーカイブ状態の検証を緩和して保持を許可し、異なる場合は新規作成と同じ検証（有効かつアサイン済み）を適用する。
   - 理由: `<select>` は一致する `<option>` が無いと先頭を選択する HTML 仕様があるため、表示側だけの対策では不十分。サーバー側でも暗黙の付け替えを拒否することで、ブラウザ差異や直接 POST を防ぐ。
   - タスクも同様に、アーカイブ済みタスクを参照している既存 allocation は更新時に元のタスクを保持する。

5. **`/health` は認証不要の独立ルートにする**
   - `app/routes/health.ts` を追加し、軽量クエリで DB 接続を確認して成功時 200 / 失敗時 503 を返す。
   - ルートは `app/routes.ts` の明示的な `RouteConfig` で管理されている（ファイル配置の自動検出ではない）。認証を要求する `app-layout` の子に入れると監視が 401 になるため、**トップレベルに `route("health", "routes/health.ts")` として登録する**。登録漏れはビルドも型検査も通ったまま実行時 404 になるため、`tests/routes/health.test.ts` に登録自体を検証するテストを置く。
   - 理由: コンテナの healthcheck と外部監視から参照するため。認証を要求すると監視用途に使えない。
   - レスポンスは可用性状態のみを含み、メンバー・案件・財務情報は一切含めない。`docker-compose.yml` にも healthcheck を追加する。

6. **ログは標準出力への 1 行 JSON にする**
   - `app/lib/log.ts` に `level` / `event` / `message` / `at` と任意コンテキストを出力する最小ロガーを追加する。記録対象は認証失敗・レート制限超過、権限拒否・保護月への書き込み拒否、アクションの未処理例外、月次締め操作に限定する。
   - 理由: コンテナ運用では標準出力が唯一の収集経路。外部ライブラリの追加は本 change の範囲を超える。
   - パスワード・パスワードハッシュ・セッション ID・原価率はログに含めない。メールアドレスは認証失敗時にドメインを除いた形で記録する。

## Risks / Trade-offs

- **外部キー有効化で既存環境が起動しなくなる** → 影響を受けるのは孤立行を持つ環境のみ。移行前に `sqlite3 ./data/kosu.sqlite "PRAGMA foreign_key_check"` を手動実行して事前確認する手順を README に明記し、検出時のメッセージに修復手順への案内を含める。
- **WAL 化で `-wal` / `-shm` ファイルが追加生成される** → README のバックアップ対象の説明を更新する。既存の「停止後コピーまたは `sqlite3 .backup`」という手順は WAL 下でも安全。
- **ログ出力による I/O 増加** → 記録対象を異常系と締め操作に限定しているため影響は軽微。成功時のリクエストログは記録しない。
- **`/health` が認証不要で公開される** → 可用性情報のみを返し、バージョンや内部構成を含めないことで情報露出を抑える。
- **`busy_timeout` による待ち時間の増加** → 既定 5 秒。書き込み競合時のみ発生し、通常運用では観測されない。

## Migration Plan

- スキーマ変更なし。新規マイグレーションは作成しない。設定と検証ロジックの追加のみ。
- 手順: アプリ停止 → バックアップ取得 → `npm run db:check`（または `sqlite3 <ファイル> "PRAGMA foreign_key_check"`）で既存データを事前確認 → 新バージョンをデプロイ → `npm run db:migrate` 内の検査で違反が無ければそのまま起動。
- 起動が停止した場合: README の修復手順に従って孤立行を確認・修復してから再起動する。修復が困難な場合はバックアップからリストアする。
- ロールバック: 旧バージョンのアプリに戻す。`journal_mode = WAL` は DB ファイルに残るが、WAL 未設定の旧バージョンでも SQLite は WAL モードの DB を通常どおり読み書きできるため、DB 側の巻き戻しは不要。
