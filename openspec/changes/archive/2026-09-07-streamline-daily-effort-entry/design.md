## Context

動機は `proposal.md - Why` を参照。ここでは実装判断に必要な現状と制約のみを述べる。

- 日別実績入力（`app/routes/work-logs.$date.tsx`）は、総稼働時間のフォーム（intent `saveWorkLog`）、案件ごとの更新フォーム（`updateAllocation`）、新規追加フォーム（`addAllocation`）、削除フォーム（`deleteAllocation`）の 4 系統に分かれている。
- 追加フォームは 1 行分しか持たないため、3 案件なら「総稼働 1 回 + 追加 3 回」で 4 回の送信とページ再読込が発生する。
- `addAllocation` は work log が存在しない場合に「先に勤務日の総稼働時間を保存してください。」を返す（`work-logs.$date.tsx:154-158`）。これが 2 段構えの原因。
- **全ルートにクライアント状態が一切存在しない**（`useState` / `useFetcher` / `useNavigation` が 0 件）。サーバレンダリングと通常のフォーム送信のみで構成されている。
- この制約により「案件を選んだらタスクを絞り込む」は実現できないが、**複数行の一括保存・前日複製・成功メッセージ・並び順変更はすべてサーバ側だけで実現できる**。クライアント状態を新規導入しないことで、既存のアーキテクチャとテストの書き方を維持できる。
- 複数行の送信は `formData.getAll()` で配列として受け取れる。HTML 仕様上、フォーム内の全 input が送信されるため、行の識別は配列の添字で紐付ける。
- 複数の submit ボタンは、押されたボタンの `name` / `value` のみが送信される。これを利用して、同一フォーム内に「保存」「前日から複製」「行の削除」を共存させる。
- 成功メッセージは `daily-plans.tsx` に前例がある（リダイレクトせず `{ saveSummary }` を返す）。他画面はリダイレクトするため成功を伝えられない。
- 案件の選択肢は `listActiveAssignmentsByMember()` の `asc(assignedAt)` 順（`project-assignments.ts:91`）。最近アサインした案件ほど下になる。
- 前 change で追加した「既存配賦の案件・タスクを維持する」検証（`validateAllocationTarget` の `existing` 引数）は、統合フォームでも必ず維持する必要がある。
- 既存の `updateAllocation` / `deleteAllocation` は、対象 allocation が**当該メンバーのもので、かつ対象日付に属すること**を確認して 404 で弾いている（`work-logs.$date.tsx:194-203`）。統合フォームでは**全行に対して同じ所有権検証が必要**で、1 行でも他者の配賦や別日の配賦が混じっていれば送信全体を 404 で拒否する。
- トランザクションによる一括適用は、`work-logs.month.tsx` の月次一括入力と `daily-allocation-plans.ts` の実績コピーに前例がある。

## Goals / Non-Goals

**Goals:**

- 1 日分の工数登録を 1 回の送信で完了できること
- 総稼働時間の事前保存を必須としないこと
- 前日の内容を再利用できること
- 保存が成功したことを利用者が確認できること
- 最近使う案件が選択肢の先頭に来ること
- クライアント状態を新規導入しないこと

**Non-Goals:**

- 案件選択に応じたタスクの動的絞り込み（クライアント状態が必要なため別 change）
- グラフ・進捗バー・ヒートマップなどの可視化（別 change）
- 週表示・月カレンダー形式の入力（別 change）
- 未入力日の可視化（別 change）
- 一覧画面のページネーション（別 change）
- タッチデバイス向けのカードレイアウト（別 change）

## Decisions

1. **4 つの intent を `saveDay` に統合し、削除は別ボタンとして残す**
   - `saveWorkLog` / `addAllocation` / `updateAllocation` を廃止し、1 つの `saveDay` にまとめる。削除は `deleteAllocationId=<id>` という name/value を持つボタンで表現する。
   - 理由: これが「1 日 1 送信」を実現する最小の変更。intent を残したままでは 2 段構えが解消しない。
   - 代替案: 旧 intent を残して統合フォームを追加 → UI が使わない経路が残り、検証すべき分岐が倍増するため不採用。
   - 影響: 旧 intent を直接 POST する連携は動かなくなる。アプリ内に該当する呼び出しは無く、対象はテストのみ。

2. **行の識別は配列の添字で紐付ける**
   - 既存行は `allocationId` を hidden で持たせ、新規行は空文字にする。`formData.getAll("allocationId")` / `getAll("projectId")` / `getAll("taskId")` / `getAll("allocatedHours")` / `getAll("note")` を同じ添字で対応させる。
   - 理由: HTML フォームは行という構造を送信しないため、添字対応が最も素直。`formData` の `getAll` は input の DOM 順を保証する。
   - 削除ボタンは `deleteAllocationId` という独立した name を使い、押されたボタンの value だけで対象を特定する。
   - **注意: `disabled` な input は送信されず配列から抜け落ちる。** そのため行単位で一部だけ `disabled` にすることはせず、ロック時はフォーム全体を無効化する（ロック時は送信自体が 423 で拒否される）。

3. **新規行には `required` を付けず、サーバ側でのみ検証する**
   - 既存の追加フォームは `projectId` と `allocatedHours` に `required` を付けていた（`work-logs.$date.tsx:514,544`）が、統合フォームでは空の新規行が常に並ぶため `required` を使うと**送信自体が HTML バリデーションで止まる**。
   - 検証はサーバ側で行う: 案件または時間のどちらかが入力されている行のみを対象とし、両方空の行は無視する。
   - 「削除」「前日から複製」ボタンには `formNoValidate` を付け、HTML バリデーションを迂回させる。押されたボタンの `name` / `value` だけが送信される仕様で分岐するため、保存時以外の送信で必須チェックが走るのは誤り。

4. **全行を先に検証し、1 件でも不正なら何も保存しない**
   - 月次一括入力（`work-logs.month.tsx`）と同じ「全行バリデーション → `db.transaction` で一括適用」の形に揃える。
   - 理由: 途中まで保存されると、利用者がどこまで反映されたか分からず、かえって混乱する。既存コードに前例があり、spec 上も「Monthly work-log bulk entry atomicity」として確立している。
   - 空行（案件も時間も未入力）は検証対象外とし、エラーにしない。

5. **総稼働時間は未保存でも受け付ける**
   - work log が存在しない場合は `saveDay` 内で作成する。存在する場合は更新する。
   - 理由: 「先に総稼働時間を保存してください」という 2 段構えが最大の摩擦だった。
   - 0 が入力された場合の扱いは、月次一括入力の「Zero-hour clearing in monthly bulk entry」に合わせず、日別画面では**総稼働 0 はバリデーションエラー**のままとする。日別画面で 0 による削除を許すと、意図せず勤務日ごと消える事故につながる。

6. **「前日から複製」は対象日が空の場合のみ実行する**
   - 対象日に allocation が 1 件でもあれば複製を拒否し、その旨を伝える。前日に work log も allocation も無ければ「複製する内容がありません」を返す。
   - 理由: 既存実績へのマージ条件（合計をどうするか、重複をどう扱うか）を定義すると仕様が一気に複雑になる。初回は「空の日を素早く埋める」用途に絞る。
   - 複製するのは前日の全 allocation 行（案件・タスク・時間・備考）。原価スナップショットは**複製時点のメンバー単価**を取り直す（既存の `addAllocation` と同じ扱い）。
   - **複製元の行のうち、アーカイブ済み案件・アサイン解除済み案件を参照する行はスキップし、何件複製してどの案件をスキップしたかを伝える。** 全部スキップになった場合は何も変更せず「複製する内容がありません」を返す。
   - 理由: 1 件アーカイブされただけで複製が全滅するのは実用的でない。複製は新規作成であり既存データを壊さないため、全か無かの原則より「使える分だけ持ってくる」を優先する。
   - 総稼働時間は、スキップで減った分を補正せず**前日の値をそのまま複製**する。複製後に未割当として画面に警告が出るため、利用者が気づける。

7. **成功メッセージはリダイレクトせずに返す**
   - `daily-plans.tsx` と同様に、`saveDay` 成功時は `{ success: "..." }` を返してリダイレクトしない。保存件数を含める。
   - 理由: リダイレクトすると成功を伝える手段が無い。またリダイレクトは画面位置を先頭に戻してしまい、追加フォームまでのスクロールを毎回強いる。
   - 副作用: ブラウザの再読み込みでフォームが再送信される警告が出る。既存の `daily-plans` も同じ挙動であり、許容する。

8. **案件の並び順は「最近使用した順 → それ以外」の 2 段階**
   - `effort-allocations` リポジトリに、メンバーの直近（既定 60 日）の実績から案件を使用日の降順で返す関数を追加し、loader で `assignedProjects` をこの順に並べ替える。残りは既存の並び（アサイン順）を保つ。
   - 理由: 「最近使った順」は一般的な工数管理ツールの標準的な挙動で、案件数が増えたときの選択コストが最も下がる。
   - 代替案: `asc(assignedAt)` を `desc` に変えるだけ → 最近アサインされた案件は上に来るが「最近使った」とは一致しないため不採用。
   - 前 change で追加した `referencedOnlyProjectIds`（参照済みだが現在アサイン外の案件）は、最近使用順の後ろに配置する。

## Risks / Trade-offs

- **旧 intent の廃止でテストの更新が発生する** → `tests/routes/work-logs.test.ts` の該当テストを `saveDay` 形式に書き換える。既存の検証意図（権限・ロック・バリデーション・案件維持）は落とさず移行する。
- **1 フォーム化で送信データ量が増える** → 1 日あたりの行数は高々十数行であり実用上問題ない。
- **行の削除が「保存」と同じフォームにあるため、編集中の内容は破棄される** → 削除ボタンに確認ダイアログは付けない（未使用の `Dialog` の導入は別 change とする）が、ボタンのラベルを「削除」のままとし、押した行が消えることを自明にする。
- **成功時にリダイレクトしないため、再読み込みで再送信される** → `daily-plans` と同じ既知の挙動。URL は変わらない。
- **最近使用順の導入でクエリが 1 本増える** → メンバー単位の直近 60 日限定の集計であり、負荷は軽微。

## Migration Plan

- スキーマ変更なし。新規マイグレーションは作成しない。
- 旧 intent を直接 POST する外部連携は存在しないため、移行作業は不要。
- ロールバック: アプリを旧バージョンに戻すのみ。DB 側の巻き戻しは不要。

- 前日ではなく「直近で実績がある日」を複製元にするか。初回は前日固定とし、要望があれば拡張する。
