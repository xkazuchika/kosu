# Design

## Context

動機と利用者の導線は `proposal.md` を参照する。現在の構成から、次の点を導入処理の設計条件とする。

- `package.json` はNode.js 22.22以上を要求する。`npm run dev` はマイグレーション後に開発サーバーを起動し、`npm start` はビルド済みサーバーだけを起動する。
- `better-sqlite3` を使うため、OS・CPU・Node.jsに適合するネイティブ部品が必要になる。第一段階はWindows x64とNode.js 22系の対応バージョンを検証対象とする。
- `drizzle.config.ts` と `app/db/config.ts` は現在の作業ディレクトリ・プロセス環境からDBとマイグレーションの場所を解決する。`.env.example` をコピーしただけで、すべてのコマンドへ同じ設定が渡る仕組みにはなっていない。
- `app/lib/env.ts` は本番の32文字以上のシークレットを検査する。`app/services/session.ts` は本番Cookieに `Secure` を付ける。導入処理は既存の認証保護を利用する。
- `docker-compose.yml` はソースからビルドし、`kosu-data` named volumeへ保存する。READMEの環境変数、停止、バックアップ例にはUnix前提の箇所がある。
- `/health`、初期セットアップ、ログインは実装済み。現在のCIはUbuntuだけで、Windows用起動エントリはない。
- 公開リポジトリは `https://github.com/xkazuchika/kosu`。既存のRelease workflowはタグとGitHub Releaseを作成するが、Node.js同梱配布物やコンテナイメージの公開処理はない。

## Goals / Non-Goals

**Goals:**

- 手動利用者とエージェントが同じ設定・導入・起動処理を実行し、説明だけの差で利用できること。
- Windowsの標準コマンドプロンプトから実行でき、PowerShellの実行ポリシー変更が不要な入口を作ること。
- 初回設定と日常の起動を区別し、短い手順と再実行時のデータ保持を両立すること。
- 実際に動く安定版と対応する導入文書を提供し、取得済みフォルダーもそのまま使えること。

**Non-Goals:**

- 第一段階でのNode.js同梱ZIP、単一実行ファイル、Windows ARM、Windowsサービス登録、HTTPS証明書の自動導入。
- 新たなDBサーバー、複数インスタンス、スキーマ変更、画面の再設計。
- コンテナレジストリへの新規公開と、エージェント製品ごとの専用スキル配布。既存Docker導入と汎用プロンプトを先に整える。

## Decisions

### 1. バッチファイルから共通のNode.js導入処理を呼ぶ

ルートに `install.bat` と `start.bat` を置き、実処理を `scripts/install/` の依存関係導入前にも動くNode.jsスクリプトへ集約する。バッチ側はNode.jsの存在確認、実行場所、終了コード、エラーを読めるウィンドウの維持を担当する。共通処理はリポジトリ位置を自身から解決して、その位置で既存コマンドを順次呼ぶ。

Windowsの `npm.cmd` 実行、引用符、スペース・日本語を含むパスを実機相当のCIで検証する。通常起動では依存関係の再取得や毎回のビルドをせず、準備不足なら `install.bat` へ案内する。

代替案はPowerShellのみの配布と、バッチへすべての処理を書き込む方法。前者は実行ポリシーの追加条件、後者は設定・エラー処理の重複が増えるため、共通Node.js処理と薄いバッチを選ぶ。

### 2. 設定を一度生成し、すべての子プロセスへ同じ環境を渡す

共通処理で設定ファイルを選択する。既定はリポジトリの `.env` とし、指定済みプロセス環境を優先して未設定値をファイルから補完する順序を文書化する。有効なデータ保存先は絶対パスとして表示し、導入・移行・起動・バックアップで同じ値を使う。

新規ファイルはランダムな32バイト以上のシークレットを含めて生成する。既存の設定は上書きせず、空欄・短すぎる値・サンプル値の場合は修正箇所を案内する。既存データや管理者アカウント、デモデータを導入処理から作り直さない。通常の直接起動ではビルド済みアプリを `NODE_ENV=production` で実行する。

代替案の毎回シークレット生成や利用者による環境変数の手入力は、セッションと操作の再現性を損なうため採用しない。

### 3. ローカル起動を既定にし、準備完了と稼働確認を区別する

直接起動の既定は `HOST=127.0.0.1`、明示したポート、利用者向けURLは `http://localhost:<port>` とする。準備ではロックファイルに基づく `npm ci`、ビルド、移行と整合性検査を順次実行する。日常起動でも移行・整合性検査後に既存のサーバーを起動する。

起動前のポート確認と起動した子プロセスの生存確認を行い、有限の待機時間内に `/health` が成功してからURLを表示する。既に動いている別プロセスのヘルス応答を成功として扱わない。停止は表示されたコンソールの `Ctrl+C` を基本とし、自分が起動した子プロセスへ終了を伝える。

既存の本番シークレットとSecure Cookieを維持し、WindowsのChromium系ブラウザでlocalhost上のセットアップ・ログイン・再ログインを検証する。HTTPの社内IP公開へそのまま広げず、共有運用はHTTPS終端を使う手順へ案内する。ブラウザ確認で支障が判明した場合は、開発モードへの切り替えで解決せず、認証保護を満たす修正案を先に確認する。

代替案の開発サーバー起動は利用者向け運用に不要な開発動作を含むため、ビルド済みサーバーを使う。

### 4. READMEの2つの入口から同じ文書と処理へ合流する

次の文書構成を基本とする。

| 文書 | 内容 |
| --- | --- |
| `docs/install/README.md` | Windows直接起動とDockerの選び方、必要なもの、最短手順 |
| `docs/install/windows.md` | ZIP／クローンからの導入、バッチ実行、初期設定、エラー時の次の操作 |
| `docs/install/docker.md` | 既存Composeの設定、ビルドと起動、volume確認、HTTPS共有時の注意点 |
| `docs/install/agent.md` | 公開URL用・取得済み用プロンプト、方法選択、取得、共通処理、完了報告 |
| `docs/install/operations.md` | 直接起動とDockerの停止・再起動・更新・バックアップ・復元 |

READMEには「インストールから起動まで、エージェントに任せられます」という短い案内と、手動ガイドへのリンクを置く。専用スキルのインストールは前提にしない。

### 5. エージェントの取得処理はバージョンを固定する

公開URLプロンプトはGitHubの安定版リリースを特定し、そのタグをGitで取得するか、そのタグのZIPを標準のダウンロード・展開手段で取得するよう指示する。既存フォルダーを上書きせず、新規の作業先を選ぶ。取得後はその版の `docs/install/agent.md` と導入エントリの存在を確認してから共通処理へ進む。

取得済み用プロンプトは現在のフォルダーとバージョンを確認し、再クローンや無断のバージョン変更をしない。Docker不可の場合は直接起動へ進む。Node.js等が不足する場合は、環境で許可される導入方法を案内・実行し、権限やツール不足で実行できない操作は明確に引き継ぐ。

完了報告は選択版、導入方式、確認済みURL、データ保存先、停止・再起動手順とする。エージェントのコマンド実行環境が終了するとサーバーも終了する場合は、持続するコンソールを利用するか、最後の起動操作を利用者へ渡す。未実行・未確認の起動を成功と報告しない。

代替案の常にmainを取得する方法はリリースと検証状態が一致しないため採用しない。最新安定版に導入機能がまだない期間は、その点を明記し、新機能を含むリリース公開と案内の有効化を対応させる。

### 6. 更新・バックアップは保存先と対応バージョンを維持する

直接起動向けには既存のSQLiteライブラリで一貫性バックアップを作れる補助コマンドを追加し、別のSQLite CLI導入を避ける。バックアップはアプリ版とDB検査結果を記録する。復元は停止状態で新しい保存先へ用意して検査し、既存の保存先は検査成功まで保持する。DBを置換する際に古いWAL／SHMを混在させない。

更新手順は停止、整合性を確認したバックアップ、新版取得、同じ設定・保存先の引き継ぎ、準備、起動確認とする。Dockerのnamed volume名は固定の `kosu_kosu-data` と仮定せず、実際のComposeプロジェクトとマウント先から確認する。現行READMEの `npm stop` と無条件削除を含む復元例を、動く停止方法と既存データを保持する復元例へ置き換える。

### 7. Windowsで導入全体を検証する

既存のUbuntu品質チェックを維持し、Windows runnerにNode.js 22系の対応バージョンを用意して、スペース・日本語のある隔離フォルダーで公開用バッチを実行する。新規導入、localhostのセットアップ・ログイン、停止、再起動、再準備、データ保持、バックアップ復元、占有ポート・設定不正時の終了を確認する。

公開URL用プロンプトは安定版タグを使うGit経路とZIP経路をレビュー・再現確認する。実装中の未公開版は隔離された候補版の取得先を使って検証し、その結果を安定版公開後の検証と区別して記録する。Dockerの手順は隔離Composeプロジェクトで既存起動とデータ保持を確認する。

## Risks / Trade-offs

- ネイティブ部品やnpmの取得が社内ネットワークで遮断される → 失敗した段階と不足条件を示す。オフライン対応とNode.js同梱配布は後続段階で扱う。
- 起動スクリプトだけではWindowsサービスと同じ常駐性を持たない → 起動コンソールを維持する必要と停止方法を明記する。
- localhostでのCookieの扱いにブラウザ差がある → 対応するWindowsブラウザでログインを検証し、未検証のブラウザまで動作保証を広げない。
- 未公開の機能が現在の安定版プロンプトから参照できない → 取得した版の導入ファイルを確認し、リリース前後の案内を分ける。
- 既存データがソースフォルダー内にある → 更新時の保存先を明示し、取得処理でそのフォルダーを置換しない。
- エージェントの権限やプロセス維持能力は製品ごとに異なる → 必要な能力と残った手動操作を文書化し、汎用プロンプトの範囲で対応する。

## Migration Plan

1. 共通設定・準備・起動処理とWindows用エントリを追加し、既存のデータと本番設定を維持する。
2. 手動・エージェントの導入文書と運用文書を追加し、READMEから到達できるようにする。
3. 隔離したWindows・Docker環境で記録された確認結果を揃え、通常の品質チェックとCIを通す。
4. 機能を含む安定版のリリース準備時に、公開プロンプトの取得先とその版の導入ファイルの対応を確認する。公開操作は既存のRelease workflowを利用する。
5. この変更自体はDBスキーマを変えない。導入機能だけを戻す場合も設定とデータは維持し、アプリ更新で移行済みDBを旧版へ戻す場合は現行の互換版バックアップ復元手順を守る。
