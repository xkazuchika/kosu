## Context

動機と対象範囲は proposal.md を参照。`reports.tsx` は実績取得には終了案件を含める一方、選択肢には `listActiveProjects` を使っている。担当者候補は無効者も含むが状態表示がない。`listEffortReportRows` は現在の担当者・案件マスタを結合するため、名称・部署・操作権限・案件種別は過去月も現在値となる。単価スナップショットとは異なる。

CSV action と loader はURL条件の解釈を重複実装している。既存テストは基本出力・財務非公開・予定実績比較をカバーするが、終了案件の画面選択からCSV出力までの操作を明示的に固める必要がある。`reports.planned-vs-actual.tsx` は案件内の役割を月次計画から取得するので、操作権限と混同しない表示が必要。

## Goals / Non-Goals

**Goals:** 閲覧用の候補と入力用の候補を分離し、既存の認可・集計を保ったまま表示と出力の整合性を高める。複数ルートにまたがる表示辞書と条件解釈を小さな共通処理にまとめる。

**Non-Goals:** 全マスタ履歴の新設、締め済み実績や財務スナップショットの書き換え、汎用レポート基盤の構築、全画面のリデザインは行わない。

## Decisions

### 1. レポート専用の候補取得

管理者は全案件と全担当者を候補にできる。一般メンバーは既存の現役案件候補に、自分の非削除実績がある終了案件だけを追加する。終了案件候補は月や他フィルターの変更で選択が消えないよう本人の全期間の実績を根拠にする。既存の現役案件公開範囲は変更しない。

候補および明細に現在の `isArchived` / `isActive` を渡し、「終了（アーカイブ）」「無効」を文字で表示する。予定対実績の明細も同様に状態を示す。入力用 `listActiveProjects` の意味を変更する案は、終了案件への新規入力を許す危険があるため採らない。一般メンバーへの追加候補は必要なID・コード・名称・状態だけに限定し、他者の履歴や財務情報を追加しない。

### 2. 現在マスタ参照を説明し、履歴固定とは区別

担当者編集には無効化によるログイン不可と実績保持、名称・部署・操作権限の変更が過去の工数レポート表示／分類に反映される説明を置く。案件編集にはアーカイブによる新規入力不可と実績保持、コード・名称・種別の変更の影響を置く。保存や状態変更ボタンの前に読める常設説明とし、確認ダイアログや追加チェックボックスは増やさない。

工数実績レポートでも、分類は現在マスタ基準であり、工数確定は当時の所属・種別の固定を意味しない旨を示す。単価・原価スナップショットと工数締め処理は変更しない。履歴テーブルの導入は今回の合意範囲外なので採らない。

### 3. 表示辞書は共通化、保存値とCSVは維持

画面上の案件種別は `billable` →「請求対象」、`internal` →「社内作業」、`non_billable` →「非請求」で統一する。担当者マスタと工数実績フィルターは「操作権限」、アサイン管理と予定対実績は「案件内の役割」とする。前者の値は「管理者」「メンバー」、後者は自由入力値を保持する。

対象は担当者・案件の一覧／新規／編集、アサイン管理、工数実績・予定対実績レポート。財務レポートの計算やCSVインポート定義は変更しない。既存CSVの10列と `admin/member`、`billable/internal/non_billable` は維持し、出力付近にコード表記を維持する旨を示す。CSVの日本語化は利用者の既存加工を破壊し得るため採らない。

### 4. 適用済み条件を単一の基準にする

URLの月・担当者・部署・操作権限・案件・種別の解釈を共通化し、loader とCSV actionで利用する。既存の無効月からワークスペース当月へのフォールバックと既存URLキーを維持し、非管理者の担当者条件は常に本人に固定する。

画面に正規化後の対象月・適用条件・工数確定状態を明示し、CSV送信先には適用済みの正規化条件を明示的に保持する。未適用の入力変更はCSV対象にしない。DB状態が同じ場合に対象行・順序・件数・時間合計が一致することを保証し、同時更新時まで画面の複製を保証するスナップショット出力は導入しない。

CSVフォームは `POST /reports/export` のリソースルートへ通常のフォーム送信を行う。画面付きルートのPOSTではCSVレスポンスが画面データとして扱われるため、ダウンロードにはリソースルートを用いる。既存の `/reports` action を再利用し、認証・本人への条件固定・CSV形式・既存URLパラメータを共通のまま維持する。

## Risks / Trade-offs

- [過去分類は変更され得る] → 編集前と閲覧時に説明し、異動／種別変更後も時間と締め状態が不変であることをテストする。
- [終了案件追加による情報露出] → 本人実績に基づく追加候補と最小限の返却項目、他者ID指定とCSVの認可テストで防ぐ。
- [候補が長くなる] → 現役／終了のグループ分けと安定したコード順を基本とし、新たな検索コンポーネントは導入しない。
- [CSVと画面の表現差] → 対象データの一致と表現の互換性を分けて説明し、既存ヘッダー・コード値・式注入対策をテストする。
- [対象外画面に旧表記が残る] → 今回の対象画面をタスクに明記し、全画面刷新へ広げない。

## Migration Plan

DBスキーマ・依存・環境変数の変更は不要。既存データの補正や再オープンは行わない。実装後にユニット／ルートテスト、型検査、lint、build、PC・モバイルの画面操作とCSV確認を実施し、互換性方針を利用説明に記録する。リリースは別の指示で行い、この変更単独のロールバックは旧アプリへ戻すだけでDB変換を必要としない。
