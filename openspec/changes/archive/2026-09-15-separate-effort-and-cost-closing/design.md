## Context

動機は proposal.md を参照。現在の `monthly_cost_closes.status` は財務 snapshot の選択と、工数・予定・CSV の編集保護の両方に利用されている。`period-locks.tsx` はレビュー開始前に原価を含む完全性を確認し、`approveMonthlyCostClose` は transaction 内で完全性と snapshot 保存を行う。

`requireOpenMonth` は複数のサービスから直接利用されているため、`period-lock.ts` だけの変更では保護が漏れる。現在の原価欠損補正は過去月の配賦も対象にできるが、選択月だけの保護確認では元データの月の原価承認を守れない。新しい補正の例外では両月を検証する。

## Goals / Non-Goals

**Goals:** 月単位で工数と原価の状態を分離し、既存の原価 status・履歴・財務 snapshot の意味を維持する。時間だけの完全性確認が原価データを必要としない構造にする。

**Non-Goals:** 全社の財務モード設定、外注費・経費、複数承認者、任意の単価上書き、給与からの単価算出、過去の財務 snapshot の再計算。

## Decisions

### 1. 同じ月レコードに独立した工数状態を追加する

`monthly_cost_closes` の既存 status は原価専用のまま保持し、`effortStatus`（open / in_review / confirmed）、レビュー者・時刻、確定者・時刻を追加する。存在しない月は両方 open とする。工数状態は DB CHECK で制約し、履歴には工数専用 eventType と工数の遷移前後の状態を追加する。既存の previousStatus / nextStatus は原価の状態を保持する。

別テーブル案も考えられるが、既存の月単位 UNIQUE と履歴への参照を使い、再オープンを一つの transaction で扱える形を選ぶ。単一 status に「工数承認済み」を追加する案では既存の原価承認判定と混同するため採用しない。

### 2. 編集保護と財務 snapshot 判定を別の読み取りにする

`getMonthlyPeriodState` を追加し、effortStatus、costStatus、isProtected と画面用の工数状態を返す。保護条件は effortStatus が open 以外、または costStatus が open 以外。

工数・予定・提出・予定確認・CSV の全読み書き経路はこの判定を使う。既存 `requireOpenMonth` は互換ラッパーとして共通判定へ移し、直接参照する import / submission を含めて漏れを防ぐ。通常の更新は状態検証と書き込みを同一 transaction に揃える。

`getMonthlyCostCloseState` は原価の状態のみを返し、`project-financials.ts` の snapshot 切替は costStatus === approved のときだけ行う。工数確定だけの場合はライブの原価を未承認の参考値として表示する。

### 3. 完全性検証を時間と原価で分ける

共通の工数完全性サービスは既存の required-submitter と日次配賦一致を再利用する。原価完全性は工数完全性に単価・契約額・予算の検証を加える。工数側から原価チェックを呼んで結果だけ捨てる構成は避ける。

工数レビュー開始と工数確定は両方、管理者権限、月・現在状態、工数完全性を immediate transaction 内で再確認し、状態とイベントを保存する。金額も月次予定確認も必須にしない。

通常の原価レビュー開始は工数確定と原価完全性を要求する。原価承認も工数確定と完全性を再確認し、既存の snapshot 保存を使用する。移行時の原価レビュー中レコードはその状態を維持し、先に工数確定することで原価承認を続行できる。

### 4. 原価欠損補正は専用操作に限定する

原価が open の場合、工数の保護中でも欠損単価の補正だけ許可する。補正の transaction 内で管理者、明示的な非負整数単価、理由、対象の欠損、対象月の範囲を確認する。実績配賦の場合は勤務日から元の月を解決し、選択月と元の月の原価状態が両方 open であることを検証する。

更新列は欠損原価のみ。工数確定・予定確認は解除せず、通常の配賦更新 route を経由させない。単価欠損を現在単価から自動補完しない。金額基準は既存の案件編集で設定し、承認済み月は既存 snapshot の値を表示する。

### 5. 再オープンは両状態をまとめて解除する

時間を修正する場合は、一つの理由付き操作で工数と原価を open に戻す。旧両状態と操作者・時刻・理由を記録し、提出状態は実績変更まで維持する。過去のイベントと snapshot は再オープン直後には削除せず、原価未承認の状態で過去 snapshot を現在の確定額として表示しない。

原価の再レビューも、工数レビュー・確定を経て行う。原価だけの複雑な差し戻し状態は今回追加しない。

### 6. 月次締めの画面を二段にする

工数領域に提出状況と配賦の不一致、レビュー・確定を配置する。原価領域は任意の折りたたみ領域とし、単価や金額の不足、原価補正、原価レビュー・承認を置く。「工数確定済み／原価未確認」を区別し、時間だけを使う人が完了できる文言にする。

入力画面の保護表示、ナビゲーション、案件財務レビューの承認表示も更新する。内部の関数名・移行方式を操作説明には出さない。

## Risks / Trade-offs

- 保護判定の参照漏れ → `getMonthlyCostCloseState` / `requireOpenMonth` の全利用箇所を分類し、工数だけ確定した月で全更新経路を回帰テストする。
- 工数確定を原価承認と誤認 → 型と表示を分離し、財務 snapshot は原価 status だけで判定する。
- 過去月原価の補正による保護迂回 → 元データの月をサーバーで解決し、選択月と同じ transaction で検証する。
- 操作が一段増える → 時間だけのチームは工数確定で完了し、原価操作は任意の領域にまとめる。
- 旧アプリは新しい工数保護を認識しない → アプリだけのロールバックを安全とは案内しない。下記の停止・復元手順を必要とする。

## Migration Plan

1. 追加 migration で工数状態・メタデータ・履歴列を追加する。旧 open は工数 open、旧 in_review は工数 in_review、旧 approved は工数 confirmed にする。
2. 旧レビュー・承認の日時と担当者を利用し、移行であることをイベントに残す。既存原価 status、イベント、財務 snapshot の値は変更しない。
3. 新規 DB と実データ形状の移行 fixture で、件数・金額・履歴・保護の維持と外部キーを検証する。
4. 通常の停止・バックアップ・移行後、新しい UI で時間のみの月と原価承認済みの月を確認する。
5. ロールバックが必要ならアプリを停止し、移行前バックアップと対応する旧アプリを復元する。移行後の入力がある場合は復元前に別途保存し、復元によって戻るデータ期間を明示する。新スキーマを保ったまま旧アプリを起動すると、工数のみの保護が失われるため禁止する。
